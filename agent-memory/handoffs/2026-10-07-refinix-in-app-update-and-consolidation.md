## V5 offline installation — accepted design and trust requirements

- **No age-based install cutoff.** Once all required assets have been successfully verified and staged, installation works without public access. The 30-day proposal is removed. Reference: `docs/releases.md` lines 241–243. Download and new Import still perform full TUF authentication, expiry and rollback checks plus lane/channel and compatibility admission. A new import with expired metadata is rejected; previously verified staging does not become a new import at installation.
- Save the verified target length/SHA-256, offer version/build identity, target path, lane, channel, schema/compatibility information, trust-root identity and verification time with the staged package. Retain the signed metadata and applicable trust chain that authenticate those values. The record is private, atomically written application state under existing ownership protections, and is never accepted from an imported archive as proof of prior verification. An unsigned JSON record or a matching checksum alone is not publisher authentication; no new cryptographic scheme or key store is needed.
- **Install performs local checks only:** authenticate the saved signed evidence through the installed trust anchor; re-hash/recount the staged bytes; require a newer offered version and matching lane/channel/trust configuration; revalidate compatibility against the actual current installation/data; then perform the full v3 archive, embedded-app, engine, disk, drain, snapshot and recovery checks. Do not invoke an online `Updater.refresh()` or apply current-time metadata expiry to the already verified download. Reject missing/inconsistent evidence, substituted bytes/record, incompatible packages and unauthorized downgrades before replacing the app or touching durable user state. Apply locally known trust invalidation; no offline action can discover a newly published revocation.
- **Compatibility is not established by `offer schema >= current` alone.** Keep the current internal N/N+1 fixtures at schema 15. Require the authenticated offer and embedded identity to agree and the target app to support the actual current schema through its supported read/migration path. A higher schema number does not authorize an unimplemented or unqualified migration. Preserve current OS/runtime compatibility checks and the controlled rollback path.
- Focused verification includes installation after the staging metadata has since expired, new expired-import refusal, staged-byte or verification-record substitution, missing signed evidence, version/lane/channel/root mismatches and unsupported schema transitions. Refusals leave the installed app and durable user state unchanged. Existing snapshot/recovery behavior remains intact.
- Trade-off: while offline, the app cannot learn about a revocation or newer release published after verification. It still enforces the locally available authenticity, integrity, compatibility and downgrade protections. This design review is not a claim that the saved-evidence or installer path already exists.
